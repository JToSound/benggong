# 《病港》第一季編年史 — 設計方案

> 用戶需求：**唔想逐章展示，而係消化晒成個第一季，好似編年史噉展示**；
> 後續章節可能回帶補完先前嘅伏筆，要能夠表達呢種前後呼應。

---

## 1. 問題陳述

### 現況
資料模型係**嚴格逐章**：

```
events.geojson（1,796 條）
  ├─ ch2  「更衣間殘肢亂葬岡之發現」
  ├─ ch2  「衣店外遇大腦怪物」
  ├─ ch3  …
  └─ ch198 …
```

每條事件有 `chapter`（單一章節）、`chapter_refs`（全部只有一個元素）。

### 為何唔夠
小說係**非線性敍事**：

- **伏筆**：ch5 一個細節，到 ch40 才解釋
- **回帶**：ch60 用一段回憶補完 ch12 嘅空白
- **多角度**：同一件事，ch30 由 A 角色視角講，ch45 由 B 角色視角補充

現時 UI 只能答「第 N 章發生咩事」，**答唔到「呢件事係咩、幾時發生、邊幾章講過」**。

### 用戶原話
> 「我唔係想逐個章節嘅內容展示，而係應該消化晒成個第一季所有內容及章節，
> 然後好似編年史噉樣展示，當中嘅有啲內容可能喺後續嘅篇章先會回帶返過去，
> 去補完先前嘅伏筆。」

---

## 2. 目標

| 目標 | 說明 |
|---|---|
| **事件為本** | 一條編年史條目 = **故事世界入面嘅一件事**，唔係「某章嘅一段」 |
| **跨章聚合** | 同一件事喺多章被提及 → 合成一條，列出所有相關章節 |
| **前後呼應** | 標示「邊章首次提及」「邊章補充／揭示」「邊章回帶」 |
| **故事時間序** | 按**故事內時間**排列，唔係敍事次序 |
| **可追溯** | 每條都連返原文章節，用戶可以跳去睇 |

## 3. 資料模型

### 新資料集：`data/public/chronicle.json`

```jsonc
{
  "version": 1,
  "season": 1,
  "generated_by": "scripts/build_chronicle.py",
  "entries": [
    {
      "id": "chr_0001",

      // ---- 內容 ----
      "title": "大本營嘅建立",
      "summary": "病毒爆發後，生還者佔據調景嶺校園建立聚居地……",

      // ---- 故事時間 ----
      // 故事內時間（唔一定等於首次提及嘅章節）
      "story_time": { "order": 12, "label": "爆發後約 3 個月" },
      // 敍事上首次出現嘅章節
      "first_mention_chapter": 2,

      // ---- 跨章聚合（核心）----
      "chapters": [
        { "chapter": 2,   "role": "first_mention", "note": "M 首次抵達大本營" },
        { "chapter": 18,  "role": "reveal",        "note": "交代大本營嘅物資分配制度" },
        { "chapter": 70,  "role": "flashback",     "note": "回帶講述建立初期嘅衝突" }
      ],

      // ---- 關係 ----
      "foreshadows": ["chr_0042"],   // 本條為呢啲條目埋下伏筆
      "pays_off":    ["chr_0007"],   // 本條解答咗呢啲條目

      // ---- 實體連結 ----
      "location_id": "loc_0004",
      "characters": ["ent_dd034941ef"],

      // ---- 可稽核 ----
      "confidence": 0.78,
      "source_event_ids": ["bg_event_0001", "bg_event_0512"],
      "review_status": "pending"
    }
  ]
}
```

### 為何要 `story_time` 同 `first_mention_chapter` 分開

呢個係編年史嘅**核心價值**。例：

| 事件 | 故事時間 | 首次提及 | 差別 |
|---|---|---|---|
| 病毒爆發 | 第 0 日 | ch1 | — |
| Dr.D 嘅研究 | 爆發前 | ch42 | **回帶** 41 章 |
| 夏晴嘅真正身份 | — | ch80 | 揭示 ch2 嘅伏筆 |

只有分開記錄，先可以表達「呢件事幾時發生」vs「讀者幾時知」。

## 4. 聚合演算法

### 問題：確定性信號太弱

實測跨章合併信號：

| 信號 | 結果 | 評價 |
|---|---|---|
| 同名（跨章） | **4 組** | 太弱 |
| 同地點 + 同角色（跨章） | 91 組 | 太多假陽性（只係「同一地方、同一角色」） |
| 同章同名重複 | 60 組 | **應該先合併**（抽取冗餘） |

**結論**：跨章事件識別需要**語意理解**，同地點推斷一樣係 LLM 任務。

### 兩階段設計

**階段 A：確定性（可重跑、零成本）**

1. **同章去重**：同一章、同一標題、描述高度重疊 → 合併（60 組）
2. **同名跨章合併**：同名且章節相距 ≤5 → 合併（4 組）
3. **故事時間排序**：用章節次序做初始 `story_time.order`
4. **產出**：`chronicle.json`（1,700+ 條，未做語意合併）

**階段 B：語意聚合（LLM，可選、可稽核）**

對每一對「候選相關事件」問 LLM：
> 「呢兩段係唔係同一件事？如果係，邊個係首次提及、邊個係補充？」

- 候選由確定性信號篩出（同地點、同角色、章節相距 ≤30）
- 輸出：合併建議 + `role` + `confidence`
- **全部入 `pending`，人手覆核才套用**（同地點推斷一致嘅治理模式）
- 用 prompt hash 快取 → 可重跑

## 5. UI 設計

### 新模式：編年史視圖（取代逐章為主）

```
┌─────────────────────────────────────────────────────────────┐
│  《病港》互動地圖           [編年史] [地圖] [關於]            │
├──────────────┬──────────────────────────────────────────────┤
│              │  第一季編年史                                 │
│  時間軸       │  ┌────────────────────────────────────────┐  │
│  ● 爆發前     │  │ ● 大本營嘅建立                          │  │
│  │           │  │   首次提及：ch2  ·  補充：ch18、ch70    │  │
│  ● 爆發      │  │   M 揹住夏晴抵達大本營……                │  │
│  │           │  │   [跳去 ch2] [跳去 ch18] [跳去 ch70]   │  │
│  ● 第一個月   │  └────────────────────────────────────────┘  │
│  │           │  ┌────────────────────────────────────────┐  │
│  ● 大本營時期 │  │ ○ Dr.D 嘅研究（回帶）                   │  │
│  │           │  │   故事時間：爆發前  ·  首次提及：ch42    │  │
│  ● 康城時期   │  │   ⚠️ 呢條回帶補完 ch2 嘅伏筆             │  │
│  │           │  └────────────────────────────────────────┘  │
│  ● 終局      │                                              │
└──────────────┴──────────────────────────────────────────────┘
```

**關鍵設計**：

1. **時間軸為骨幹** —— 左側係故事時間分期，右側係該期嘅事件卡
2. **事件卡顯示章節標籤** —— 「首次提及：ch2 · 補充：ch18、ch70」可以逐個跳
3. **回帶標記** —— 故事時間早過首次提及嘅條目，用唔同視覺（例如虛線邊框 + ⚠️）
4. **伏筆關係** —— 「呢條補完 X 嘅伏筆」可以點擊跳去
5. **地圖仍然存在** —— 點事件卡會喺地圖高亮相關地點，但**唔再以章節為主軸**

### 與現有 UI 嘅關係

| 現有 | 新 |
|---|---|
| 章節條（1–198） | **保留**，但降級為「篩選器」——點某章會篩出該章相關嘅編年史條目 |
| 事件列表（本章事件） | **取代**為編年史條目（跨章） |
| 地圖 | 保留，跟編年史條目高亮 |

## 6. 實作計劃

| 階段 | 內容 | 風險 |
|---|---|---|
| **1** | `chronicle.schema.json` + `build_chronicle.py`（階段 A 確定性） | 低 |
| **2** | 編年史 UI（時間軸 + 事件卡） | 中 |
| **3** | LLM 語意聚合（階段 B）+ 人手覆核流程 | 中（成本、需覆核） |
| **4** | 伏筆／回帶關係抽取 | 高（需語意理解） |

**階段 1–2 可以即刻做**，階段 3–4 需要用戶確認（涉及 LLM 成本同覆核工作量）。

## 6.5 模型存取（實測對比）

### 首選（用戶指定）：`deepseek-v4.1-flash`
❌ **HTTP 402 額度不足** —— 細請求過得，批次被拒。

### 免費模型對比（同一批 12 條、同一 prompt）

| 模型 | 速度 | 結果 |
|---|---|---|
| **`nvidia/nemotron-3-super-120b-a12b:free`** | **18.4s** | ✅ JSON 可靠 ← **採用** |
| `deepseek/deepseek-v4-flash-0731:free` | 220s（波動大） | ✅ 但慢 12 倍 |
| `nex-agi/nex-n2.5-pro:free` | 118.6s | ⚠️ JSON 格式錯 |
| `nvidia/nemotron-3.5-lightning:free` | 165.0s | ⚠️ JSON 格式錯 |
| `qwen/qwen3.8-27b:free` | — | ❌ HTTP 429 |
| `z-ai/glm-5.2:free` | — | ❌ HTTP 429 |
| `google/gemma-4-31b-it:free` | — | ❌ HTTP 429 |
| `inclusionai/ling-3.0-flash-sante:free` | — | ❌ HTTP 400 |
| `thinkingmachines/inkling:free` | — | ❌ HTTP 403 |

**結論**：22 個免費模型之中只有 **2 個**真正可用，而 nemotron 比
deepseek 快 **12 倍**。→ 採用 nemotron。

⚠️ **「免費」唔等於「可用」**：免費池係共享額度，實測大量模型回
429／403。所以揀模型要**實測連續呼叫嘅吞吐**，唔可以只睇單次延遲。

### 3 個失效模型嘅替換（用戶指出已無法調用）

| 用途 | 舊（已下架） | 新（實測） |
|---|---|---|
| `ORCHESTRATOR_MODEL` | `stealth/ox-alpha` | `nvidia/nemotron-3-super-120b-a12b:free` |
| `CODING_MODEL` | `stealth/ox-alpha` | `cohere/north-mini-code:free`（6.5s，代碼專用） |
| `EXTRACTION_MODEL` | `minimax/minimax-m3:free` | `nvidia/nemotron-3-super-120b-a12b:free` |
| `VISION_MODEL` | `stealth/ox-alpha` | `~deepseek/deepseek-flash-latest`（免費池冇視覺模型，$0.15/M） |
| 地點推斷 | `stealth/union-alpha` | `nvidia/nemotron-3-super-120b-a12b:free` |

### 兩個實測踩到嘅坑

**1. Reasoning 模型會燒爆 token 預算**
`deepseek-v4.1-flash` 係 reasoning 模型 —— 先推理才出答案。
`max_tokens=4000` 會出現 `finish_reason=length`、`content` 變 `null`。
→ 提升到 16,000，並將 `OPENROUTER_EFFORT` 設為 `low`
  （呢個任務只需要分類，唔需要深度推理）。

**2. 中途斷咗要續跑**
全量 1,716 條要 132 次呼叫（免費模型批次 8）。中途遇過 402、
網絡中斷。→ 加 `--resume`，跳過已經處理過嘅條目。

## 6.8 逐章時期邊界（階段 3）

### 為何要逐章審視而唔係抽樣

階段 2 用抽樣 24 章得出嘅邊界（「爆發初期 1–15」）**唔準確** ——
逐章審視顯示 **ch3 就已經進入大本營**。

→ 用 10 個子代理**逐章**審視（每個約 20 期），讀每一期開頭 170 字。

### 關鍵發現：故事喺地點上係非線性嘅

角色喺「大本營」同「艾寶琳／康城」之間**來回走動**：

```
ch141-144 大本營 → ch145-147 艾寶琳 → ch148-150 大本營 → ch151-160 康城
```

**時期唔可以當成單調遞進** —— 呢個係抽樣版本睇唔到嘅。

### LLM 逐條判斷嘅系統性錯誤

一致率只有 **67.8%**。抽樣核實（4 個案例，代理全部係對嘅）：

| 章節 | 內容 | LLM 判 | 實際 |
|---|---|---|---|
| ch89 | 病腦大廚煮童（不良人 arc） | 康城時期 ✗ | **大本營** |
| ch77 | 病童哀哭聲、刀具架 | 康城時期 ✗ | **大本營** |
| ch113 | 莎士比亞違禁品、**艾寶琳共和國** | 大本營時期 ✗ | **康城** |
| ch169 | 飛虎隊錄影回帶 | 終局 ⚠️ | 各有道理 |

**根因**：LLM 只睇標題 + 150 字摘要，缺乏**章節上下文**。

### 套用規則

- **非回帶**條目 → 用所屬章節嘅時期（章節係硬約束）
- **回帶**條目 → **保留**原判斷（故事時間可以同章節唔同，
  例如 ch169 回帶病毒爆發當日）
- 冇邊界資料嘅章節 → 保留原判斷

**修正 391 條**。

### ⚠️ 陷阱：前端必須認得新嘅 `source` 值

階段 3 加咗 `chapter_boundary`，但前端只認 `llm_period`
→ **391 條顯示「未判定」**。

**呢個 bug 踩過兩次**（第一次係 `prior_corrected` → `chapter_order`）。
→ 加資料層測試 `FRONTEND_ACCEPTS`（同前端刻意重複，捉唔一致）。

## 7. 誠實嘅限制

1. **`story_time` 唔一定準確** —— 小說冇明確日期。只能由章節次序 + 文中線索
   （「三個月後」）推斷。**冇線索就標 `unknown`，唔可以估。**
2. **跨章合併一定有錯** —— 同一件事喺唔同章用唔同措辭講，確定性信號捉唔到。
   階段 B 嘅 LLM 都會有錯，所以**必須人手覆核**。
3. **伏筆關係最難** —— 「呢段係伏筆」需要理解作者意圖，係主觀判斷。
   建議只做**高信心**嘅（例如文中明文「原來當日……」）。

## 8. 需要用戶確認嘅問題

1. **編年史取代定並存？** 建議**並存**：編年史做預設，章節條保留做篩選。
2. **`story_time` 點分？** 建議按故事內嘅**時期**（爆發前／爆發／初期／
   大本營時期／康城時期／終局），唔係硬性日期。
3. **要唔要做階段 3（LLM 語意聚合）？** 涉及成本 + 人手覆核。
4. **伏筆關係要唔要做？** 最難，但亦係用戶最想要嘅效果之一。
